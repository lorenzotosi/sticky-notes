# Persistent vertical-slice verification scope

The R2 acceptance boundary connects the Vue frontend, Spring Boot REST API, shared Kotlin domain, and MongoDB. The tests listed here exercise individual boundaries; mocked frontend and controller tests do not prove a complete browser-to-database journey. Executed HTTP/MongoDB results are recorded in [R3 evidence](R3.md), which also records the browser review of the Vue interface.

## Reproduce from a clean clone

Use JDK 21, the pinned Node.js version, Google Chrome, and a running Docker engine. Start from a clean source checkout; do not copy `build`, `node_modules`, `dist`, or project caches.

`--no-build-cache` ensures no cached outputs are reused. Run the complete test suite across domain, backend, and frontend:

```sh
./gradlew :commons:check :backend:check :frontend:frontendCheck \
  --no-build-cache --no-configuration-cache
```

Start the [development MongoDB instance](../development.md#full-stack-end-to-end-execution), then inspect the browser-to-database journey manually:
```sh
# Terminal 1: launch backend with local profile
./gradlew :backend:bootJar
java -jar backend/build/libs/backend.jar --spring.profiles.active=local

# Terminal 2: launch Vite dev server (proxies /api to 8080)
./gradlew :frontend:frontendInstall
cd frontend
npm run dev
```

Navigate to http://localhost:5173. Create, edit, and delete notes. Reload the browser page (F5) and restart the backend server; verify that notes and column counts remain identical.

## Exercised layers

`NoteControllerTest` calls controller methods with a mocked service. Frontend component, API-client, and composable tests use mocked HTTP or client responses; they exercise presentation, revision propagation, prevalidation, and state coordination.

`MongoBoardRepositoryIntegrationTest` exercises real MongoDB persistence, conditional saves, and backend-context restart without HTTP. `ChecklistHttpIntegrationTest` additionally connects HTTP, the application service, shared JVM domain, and MongoDB; its observed results are linked above.

The [product requirements](../requirements.md) and [API contracts](../contracts.md) define acceptance criteria. A manual browser journey must record the source revision, environment, steps, and observed results before being presented as end-to-end acceptance evidence.

## Real consumers and integration

The frontend consumes the real HTTP API via `boardClient.js` and state coordination composable `useBoard.js`:
- **Optimistic Concurrency**: Every mutation dispatches the current `expectedRevision`. Upon receiving HTTP `409 REVISION_CONFLICT`, the state automatically fetches the latest board snapshot and updates the UI without losing unsubmitted draft text.
- **Component Architecture**: `NoteCard.vue` and `NoteEditor.vue` strictly encapsulate presentation styles using `<style scoped>`. Color badges and cards use semantic CSS class bindings mapped to domain colors, preventing arbitrary CSS injection.
- **Accessible Interactions**: Deletion uses an inline confirmation flow with default cancellation. Form controls provide character counters (1..500 UTF-16 code units) and localized screen-reader announcements via `aria-live`.
- **Database Boundary**: `MongoBoardRepository` persists the entire board aggregate root within a single document (`_id: "main"`), maintaining Compare-And-Set guarantees on the `revision` field.
