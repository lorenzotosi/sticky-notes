# Persistent vertical-slice verification scope

The R2 acceptance boundary connects the Vue frontend, Spring Boot REST API, shared Kotlin domain, and MongoDB. The tests listed here exercise individual boundaries. Mocked frontend and controller tests do not prove a complete browser-to-database journey. [R3 evidence](R3.md) records the executed HTTP/MongoDB results and the browser review of the Vue app.

## Reproduce from a clean clone

Use JDK 21, the pinned Node.js version, Google Chrome, and a running Docker engine. Start from a clean source checkout. Do not copy `build`, `node_modules`, `dist`, or project caches.

`--no-build-cache` stops reuse of cached outputs. Run the complete test suite across domain, backend, and frontend:

```sh
./gradlew :commons:check :backend:check :frontend:frontendCheck \
  --no-build-cache --no-configuration-cache
```

Start the [development MongoDB instance](../development.md#full-stack-end-to-end-execution), then inspect the browser-to-database journey manually:
```sh
# Terminal 1: launch backend with local profile
./gradlew :backend:bootJar
java -jar backend/build/libs/backend.jar --spring.profiles.active=local

# Terminal 2: launch Vite dev server (proxies /api to 8080)
./gradlew :frontend:frontendInstall
cd frontend
npm run dev
```

Navigate to http://localhost:5173. Create, edit, and delete notes. Reload the browser page (F5) and restart the backend server. Check that notes and column counts remain identical.

## Exercised layers

`NoteControllerTest` calls controller methods with a mocked service. Frontend component, API-client, and composable tests use mocked HTTP or client responses. They exercise presentation, revision propagation, prevalidation, and state coordination.

`MongoBoardRepositoryIntegrationTest` exercises real MongoDB persistence, conditional saves, and backend-context restart without HTTP. `ChecklistHttpIntegrationTest` also connects HTTP, the application service, shared JVM domain, and MongoDB. R3 records its observed results.

The [product requirements](../requirements.md) and [API contracts](../contracts.md) define acceptance criteria. A manual browser journey must record the source revision, environment, steps, and observed results before being presented as end-to-end acceptance evidence.

## Real consumers and integration

The frontend consumes the real HTTP API through `boardClient.js` and the state composable `useBoard.js`:
- Every mutation sends the current `expectedRevision`. On HTTP `409 REVISION_CONFLICT` the composable fetches the latest board snapshot and updates the UI. Unsubmitted draft text stays in place.
- `NoteCard.vue` and `NoteEditor.vue` scope their styles with `<style scoped>`. Color badges and cards bind semantic CSS classes to domain colors, so content cannot inject CSS.
- Deletion uses an inline confirmation flow that cancels by default. Form controls show character counters (1..500 UTF-16 code units) and localized screen-reader announcements through `aria-live`.
- `MongoBoardRepository` persists the whole board as one document (`_id: "main"`). The write on the `revision` field is a compare-and-set.

| Artifact | Produced location |
| --- | --- |
| Executable backend JAR | `backend/build/libs/backend.jar` |
| Compiled frontend distribution | `frontend/dist/` |
| Shared KMP domain library (JVM) | `commons/build/libs/*-jvm.jar` |
| Local NPM domain package | `commons/build/npm/sticky-notes-domain/` |

Production code uses MongoDB persistence and the shared multiplatform domain. Test mocks and seeded boards belong to the verification suites. They do not establish a passing browser-to-database journey by themselves.
