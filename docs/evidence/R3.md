# R3 HTTP and persistence evidence

This document records checklist API and concurrency evidence through Spring HTTP, the application service, the shared JVM domain, and a real MongoDB server. The checklist run below was executed locally on 2026-10-12. The concurrency section distinguishes an inspected Gradle report from a maintainer-reported mutation check. These results do not cover the Vue interface, a MongoDB server restart, separate JVM processes, or the full R3 integration gate.

The accepted behavior is described in [domain rules](../domain.md) and [API contracts](../contracts.md#4-checklist-endpoints-r3). Test setup and execution are described in the [testing guide](../testing.md#checklist-http-and-mongodb-integration-tests-r3).

## Checklist HTTP and persistence

### Exercised scenarios

The [MongoDB HTTP suite](../../backend/src/integrationTest/java/stickynotes/integration/ChecklistHttpIntegrationTest.java) exercises these scenarios:

- `checklistCommandsPersistAndSurviveBackendRestart` creates the twentieth item, returns its generated UUID from the target note, rejects an additional item, renames and toggles it, restarts the backend context, and deletes it. It checks label normalization, complete snapshots, revision increments, and preservation of other items and notes.
- `completionAndReopeningRespectChecklistAndWip` moves an incomplete note from `TODO` to `DOING`, rejects completion, completes the item, and enters `DONE`. Addition, renaming, toggling, and deletion are all rejected in `DONE`. Reopening fails while another note fills WIP, succeeds after freeing that slot, and preserves the checklist. An explicit `false` update then succeeds in `DOING`.
- `emptyChecklistAllowsCompletion` moves an unblocked `DOING` note with no items to `DONE`.
- `invalidLabelPreservesTheStoredDocument`, `missingItemPreservesTheStoredDocument`, and `staleRevisionPreservesTheStoredDocument` verify representative rejected commands and HTTP error metadata.
- `emptyBoardContainsEverySnapshotField` protects required snapshot fields whose values equal Kotlin constructor defaults.

Successful responses are compared with the MongoDB repository snapshot and a fresh GET. Each rejected command compares the entire raw MongoDB document and GET response before and after the request, including the revision. The continuous journey does not reset the board between steps.

The [focused HTTP suite](../../backend/src/test/java/stickynotes/api/ChecklistHttpTest.java) uses a mocked service to check representative JSON type failures, omitted fields versus explicit null and `false`, revision validation, whitespace-only item IDs (including URL-encoded non-breaking spaces), and neutral infrastructure errors. The item-ID regression verifies HTTP 400 and zero service calls for PATCH and DELETE. Domain permutations and conditional-save orchestration remain in the existing shared-domain and application service tests.

### Reproduction environment and command

The observed environment used macOS on x86_64, Temurin JDK 21.0.6+7, Gradle 9.7.1, and Docker Engine 29.8.2. MongoDB used the image pinned by `compose.test.yaml`: `mongo@sha256:f071cbf97a6e52fb7f07ce9ca5d862ad79876bf0eba9ba97758337d740449638`.

Use JDK 21 and a running Docker engine, with port `127.0.0.1:27018` available. Run from the repository root:

```sh
./gradlew :backend:test \
  --tests stickynotes.api.ChecklistHttpTest \
  --tests stickynotes.application.BoardServiceTest \
  :backend:integrationTest :backend:spotlessJavaCheck \
  --no-configuration-cache --no-daemon
```

The integration task creates the isolated MongoDB container and finalizes with cleanup. The HTTP suite creates a unique database, seeds it before each test, and drops it after the class. The observed run removed the test container and network.
