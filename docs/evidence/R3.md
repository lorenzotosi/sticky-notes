# R3 acceptance evidence

The R3 gate covers the complete Kanban behaviour: movement between columns, work in progress limits, blockers, checklists, guarded completion and reopening, ordering inside a column, conditional writes under concurrency, and accessible interaction. The accepted behaviour is described in [domain rules](../domain.md), [API contracts](../contracts.md), and [UI and interaction design](../ux.md). This document records the executed results of that scope, the browser review of the interface, and the limits of the evidence.

The gate does not include accounts, authentication, real-time collaboration, or the delivery of the application as containers, which belong to the later gates. The product scope is stated in [requirements](../requirements.md).

## Concurrent commands and conditional writes

The [concurrency guide](../concurrency.md) describes the conditional-write boundary. The [testing guide](../testing.md#concurrent-http-commands-and-mongodb-r3) describes the three implemented scenarios and a repeatable mutation procedure. The executed run of the scenarios is recorded in the observed results below.

`ConcurrentBoardTest` starts two independent Spring application contexts in one JVM, each with a random loopback HTTP port and its own MongoDB client, and points them at the same unique database. Repository spies share a `CyclicBarrier` at the start of `save()`, so both services load and validate their commands before either reaches the database. The scenarios cover the last free work in progress slot, two competing edits of the same note, and a limit change competing with a movement on the same revision. Each scenario requires one success, one `409 REVISION_CONFLICT`, a single stored snapshot at the next revision, and no lost update.

The revision-filter mutation procedure in the [testing guide](../testing.md#revision-filter-mutation-check) is a repeatable check that confirms the guard is detected when it is removed. It is not part of the executed run recorded here.

## Checklist HTTP and persistence

### Exercised scenarios

The [MongoDB HTTP suite](../../backend/src/integrationTest/java/stickynotes/integration/ChecklistHttpIntegrationTest.java) exercises these scenarios:

- `checklistCommandsPersistAndSurviveBackendRestart` creates the twentieth item, returns its generated UUID from the target note, rejects an additional item, renames and toggles it, restarts the backend context, and deletes it. It checks label normalization, complete snapshots, revision increments, and preservation of other items and notes.
- `completionAndReopeningRespectChecklistAndWip` moves an incomplete note from `TODO` to `DOING`, rejects completion, completes the item, and enters `DONE`. Addition, renaming, toggling, and deletion are all rejected in `DONE`. Reopening fails while another note fills WIP, succeeds after freeing that slot, and preserves the checklist. An explicit `false` update then succeeds in `DOING`.
- `emptyChecklistAllowsCompletion` moves an unblocked `DOING` note with no items to `DONE`.
- `invalidLabelPreservesTheStoredDocument`, `missingItemPreservesTheStoredDocument`, and `staleRevisionPreservesTheStoredDocument` verify representative rejected commands and HTTP error metadata.
- `emptyBoardContainsEverySnapshotField` protects required snapshot fields whose values equal Kotlin constructor defaults.
- `oversizedChunkedCommandPreservesTheStoredDocument` sends an otherwise valid checklist toggle with 65,537 bytes and no `Content-Length`. It verifies `413 PAYLOAD_TOO_LARGE` and preservation of the complete MongoDB document and GET snapshot, including the revision.
- `invalidCommandJsonPreservesTheStoredDocument` verifies `400 INVALID_REQUEST` for an unknown field in a WIP command. The rejected command preserves the complete stored document and GET snapshot.

Successful responses are compared with the MongoDB repository snapshot and a fresh GET. Each rejected command compares the entire raw MongoDB document and GET response before and after the request, including the revision. The continuous journey does not reset the board between steps.

The [focused HTTP suite](../../backend/src/test/java/stickynotes/api/ChecklistHttpTest.java) uses a mocked service to check representative JSON type failures, omitted fields versus explicit null and `false`, revision validation, whitespace-only item IDs including URL-encoded non-breaking spaces, and neutral infrastructure errors. Its three server-failure cases exercise database unavailability, an invalid persisted snapshot, and an unexpected exception. Captured console logs contain the error code and HTTP status and omit request content, exception details, and credential fixtures. The item-ID regression verifies HTTP 400 and zero service calls for PATCH and DELETE. Domain permutations and conditional-save orchestration remain in the existing shared-domain and application service tests.

The [body-limit HTTP suite](../../backend/src/test/java/stickynotes/api/CommandBodyLimitHttpTest.java) exercises seven cases with a mocked service. Oversized POST, PUT, PATCH, and DELETE requests with known lengths return `413` without a service call. A chunked body containing 65,537 UTF-8 bytes but only 65,536 characters also returns `413`. A valid JSON command padded to exactly 65,536 bytes succeeds with both known-length and chunked transfer, preserving the non-ASCII label passed to the service.

The [command JSON HTTP suite](../../backend/src/test/java/stickynotes/api/CommandJsonHttpTest.java) exercises nineteen cases across note creation, note updates, movement, WIP, and blockers. It rejects unknown fields, malformed or non-object bodies, wrong scalar types, numeric enum ordinals, invalid revisions, and note PATCH requests without a non-null mutable value. Invalid enum names, indices, and WIP limits retain the catalogued codes and field metadata. Successful requests verify that null and omitted optional note fields preserve the default creation color and unchanged PATCH fields, including non-ASCII text. Checklist null rejection remains covered by its existing suite.

`BoardBootstrapTest.allowsStartupWhenTheMongoOperationTimesOutWithoutRetry` protects startup continuation when Spring Data translates a MongoDB operation timeout. `MainTest.livenessIsUpWithoutDatabase` exercises startup and HTTP liveness with the real client against an unreachable MongoDB address, while verifying that username and password fixtures remain absent from startup logs.

The [manual recovery procedure](../testing.md#mongodb-outage-and-recovery-r3) was exercised with the packaged backend on port 8081 and an isolated MongoDB container on port 27019. A note was created at revision 1. During the outage, liveness returned `200 UP`; readiness, GET, and a valid WIP update returned `503` in about five seconds, while malformed JSON returned `400`. After restarting MongoDB, the same backend recovered, the full BSON document and GET snapshot matched their saved copies, and a WIP update returned revision 2. Health bodies contained only `status`; management exposed only health and empty info. The temporary backend, container, and anonymous volumes were removed afterward.

## Browser review of the interface

The interface was reviewed in Google Chrome against a running backend and MongoDB instance, with a board holding the four note colours, a blocked note, a note in `DOING` with a completed checklist item, a note in `DONE`, and a 197 character note containing a 42 character unbroken token.

Two windows of the same board were opened on the same note. The first window saved a new content. The second window, still holding the previous revision, submitted a different content and received the conflict response: the interface announced the conflict through a `role="alert"` notice, reloaded the board, and kept the typed text in the editor. The stored board kept the content of the first window, at the next revision, with the original number of notes. No second note was created and no automatic resubmission occurred.

The keyboard, focus, label, contrast, zoom, and viewport results of the review are recorded in [Accessibility verification](../accessibility.md).

## Reproduction environment and commands

The results were observed on the source revision `169dcfb`, which carries the interface corrections, on the branch that closes the R3 gate. The observed environment used macOS 15.8.1 on x86_64, Eclipse Temurin JDK 21.0.6, Gradle 9.7.1, Node.js 24.21.0, Docker Engine 29.8.2, and Google Chrome 155. MongoDB used the image pinned by `compose.test.yaml`: `mongo@sha256:f071cbf97a6e52fb7f07ce9ca5d862ad79876bf0eba9ba97758337d740449638`.

Run the complete suite with JDK 21 and a running Docker engine from the repository root:

```sh
./gradlew fullTest --rerun-tasks --no-configuration-cache --no-daemon
```

Every test task is executed again, so the reports below belong to this run and to this toolchain. The configuration cache is disabled because the Spotless task reports a stale local cache when it is reused, as described in the [development guide](../development.md#gradle-configuration-cache). The integration task creates the isolated MongoDB container and finalizes with cleanup. To rebuild the documentation artifact and to check the license headers:

```sh
./gradlew documentation verifyLicense --no-daemon
```

For the browser review, start the backend against a MongoDB instance and the development server, then open `http://localhost:5173`:

```sh
MONGODB_URI=mongodb://127.0.0.1:27019/sticky_notes PORT=8080 \
  ./gradlew :backend:bootRun --args='--spring.profiles.active=local'
cd frontend && npm run dev
```

## Limits of this evidence

- The automated suites and the browser review cover the behaviour of the shared domain, the HTTP interface, the persistence layer, and the Vue interface. A review of the complete delivery, the packaged artifacts, and the installation on a clean machine belongs to the later delivery gate.
- The browser review exercised the interface in one browser. No assistive technology was run and no automated end-to-end suite covers the interface, which is part of the later delivery gate.
- The concurrency evidence covers two application contexts in one JVM against one MongoDB server. It does not cover separate operating system processes, a database failover, or a network partition.
- The manual MongoDB outage and recovery journey is a separate procedure and is not part of the automated run.
