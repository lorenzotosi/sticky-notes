# Shared-domain acceptance evidence

This document describes the R1 acceptance boundary: shared domain scenarios on JVM and a real headless browser, consumption from Java and Vue, and build-produced artifacts. This evidence does not cover REST, MongoDB, server-side revision enforcement, or the full Kanban UI.

## Reproduce from a clean clone

Use JDK 21, Node.js 24.21.0, and Google Chrome. Clone the reviewed task revision into a new directory; do not copy `build`, `node_modules`, `dist`, or project caches.

The Gradle dependency/toolchain download cache may be shared. `--no-build-cache` prevents reuse of cached task outputs; the new clone has no project outputs or task history. The frontend task graph generates `commons/build/npm/sticky-notes-domain` before running `npm ci`, tests, and Vite.

Compare `commons/build/test-results/jvmTest/` and `commons/build/test-results/jsBrowserTest/`. Both must execute the same shared scenarios, with zero failures, errors, or skipped tests. Browser report names include the Chrome/platform suffix, which should be removed when comparing scenario names. Also inspect `backend/build/test-results/test/` and the Vitest output.

To check shared report equivalence with Python's standard library:

```sh
python3 - <<'PY'
from collections import Counter
from pathlib import Path
import re
import xml.etree.ElementTree as ET

scenarios = []
for target in ('jvmTest', 'jsBrowserTest'):
    cases = [case for file in Path('commons/build/test-results', target).glob('*.xml')
             for case in ET.parse(file).getroot().iter('testcase')]
    assert cases, target
    assert all(case.find(tag) is None for case in cases for tag in ('failure', 'error', 'skipped'))
    scenarios.append(Counter((case.get('classname').removeprefix('jsBrowserTest.'),
                              re.sub(r'\[.*\]$', '', case.get('name'))) for case in cases))
assert scenarios[0] == scenarios[1]
print('Identical passing scenarios:', sum(scenarios[0].values()))
PY
```

## Real consumers

`backend/src/test/java/stickynotes/DomainInteropTest.java` calls `JvmBoardFacade` from Java and checks WIP saturation, incomplete checklist rejection, and lowering WIP below occupancy. The HTTP server in the recorded R1 revision exposed only health; this is a Java library consumption proof, not an implemented board API.

`frontend/src/App.vue` imports `evaluateBoardCommand` from `sticky-notes-domain`. It sends the current snapshot and a `CREATE_NOTE` command, renders the returned board on success, and preserves the draft and existing notes on failure. `App.test.js` uses the real generated package, without mocking the facade, and checks recovery after a rejected 501-unit submission. `domain.test.js` separately tests the facade's JSON boundary and WIP/checklist rules. Vitest uses jsdom; the independent Kotlin common suite uses ChromeHeadless.

The regression test for note creation first failed with `IllegalArgumentException`: creation appended a TODO note after DOING/DONE notes. `Board.createNote` now applies the existing canonical-order helper before constructing the next board. No consumer-specific rule was added.
