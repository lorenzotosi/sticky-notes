# Shared-domain acceptance evidence

This document describes the R1 acceptance boundary: shared domain scenarios on JVM and a real headless browser, consumption from Java and Vue, and build-produced artifacts. REST, MongoDB, server-side revision enforcement, and the full Kanban UI belong to later integration gates.

## Reproduce from a clean clone

Use JDK 21, Node.js 24.21.0, and Google Chrome. Clone the reviewed task revision into a new directory; do not copy `build`, `node_modules`, `dist`, or project caches. On macOS:

```sh
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
export CHROME_BIN="/Applications/Google Chrome.app/Contents/MacOS/Google Chrome"
./gradlew fullBuild verifyLicense --no-daemon --no-build-cache
```

The Gradle dependency/toolchain download cache may be shared. `--no-build-cache` prevents reuse of cached task outputs; the new clone has no project outputs or task history. The frontend task graph generates `commons/build/npm/sticky-notes-domain` before running `npm ci`, tests, and Vite.

Compare `commons/build/test-results/jvmTest/` and `commons/build/test-results/jsBrowserTest/`. Both must execute the same shared scenarios, with zero failures, errors, or skipped tests. Browser report names include the Chrome/platform suffix, which should be removed when comparing scenario names. Also inspect `backend/build/test-results/test/` and the Vitest output.

To check shared report equivalence with Python's standard library:

```sh
python3 - <<'PY'
from collections import Counter
from pathlib import Path
import re
import xml.etree.ElementTree as ET

scenarios = []
for target in ('jvmTest', 'jsBrowserTest'):
    cases = [case for file in Path('commons/build/test-results', target).glob('*.xml')
             for case in ET.parse(file).getroot().iter('testcase')]
    assert cases, target
    assert all(case.find(tag) is None for case in cases for tag in ('failure', 'error', 'skipped'))
    scenarios.append(Counter((case.get('classname').removeprefix('jsBrowserTest.'),
                              re.sub(r'\[.*\]$', '', case.get('name'))) for case in cases))
assert scenarios[0] == scenarios[1]
print('Identical passing scenarios:', sum(scenarios[0].values()))
PY
```

## Real consumers

`backend/src/test/java/stickynotes/DomainInteropTest.java` calls `JvmBoardFacade` from Java and checks WIP saturation, incomplete checklist rejection, and lowering WIP below occupancy. The current HTTP server still exposes only health; this is a Java library consumption proof, not an implemented board API.

`frontend/src/App.vue` imports `evaluateBoardCommand` from `sticky-notes-domain`. It sends the current snapshot and a `CREATE_NOTE` command, renders the returned board on success, and preserves the draft and existing notes on failure. `App.test.js` uses the real generated package, without mocking the facade, and checks recovery after a rejected 501-unit submission. `domain.test.js` separately tests the facade's JSON boundary and WIP/checklist rules. Vitest uses jsdom; the independent Kotlin common suite uses ChromeHeadless.

The C05 regression test first failed with `IllegalArgumentException`: creation appended a TODO note after DOING/DONE notes. `Board.createNote` now applies the existing canonical-order helper before constructing the next board. No consumer-specific rule was added.

## Review and integration evidence

The baseline is main commit `d21bab1a1d837d374026f4c15514ad54130363db`, containing T027 (#35), after T026 (#33). Its [main CI run](https://github.com/lorenzotosi/sticky-notes/actions/runs/36692677655) completed successfully. T026's [main CI run](https://github.com/lorenzotosi/sticky-notes/actions/runs/36428914455) also completed successfully. These runs prove the prerequisites, not the unmerged T028 changes.

The two authors must complete the task's cross-review: explain that the planned Mongo save filters by board ID and the read revision, increments revision only on a successful save, and reports conflict instead of retrying blindly; demonstrate the real Vue import and trace it to `BoardEngine`. This corresponds to the concurrency expectations in [C21](../verification.md#c21) and [C22](../verification.md#c22), but CAS is still a design for later persistence tasks, not functionality tested by R1.

Gate closure also requires peer review, merge, a successful CI run for the merged task revision on main, and inspection of any automatically eligible release. Those actions cannot be inferred from a local build. R1 is a functional milestone, not a SemVer number; `.releaserc.json` calculates releases from eligible commits.

This evidence follows `12-multiplatform_slides.pdf`, physical pages 107–126 (real cross-language consumption), and `07-ci_slides.pdf`, physical pages 7–10 (clean, repeatable verification). It prevents stale generated packages and tests that pass without exercising the consumer.
