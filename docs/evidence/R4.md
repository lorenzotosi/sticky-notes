# R4 acceptance evidence

The R4 gate covers the reproducible delivery: the container images, the Compose stack, the automated checks against the running stack, the browser journeys, the release bundle and the records that identify it, the backup and restore of the data, and the installation on a clean machine. The accepted behaviour is described in [requirements](../requirements.md), [architecture](../architecture.md), and [deployment](../deployment.md). The repeatable procedures are described in the [testing guide](../testing.md) and in the [release checklist](../release-checklist.md). This document records the results that were executed.

The results were observed on macOS 15.8.1 on x86_64, with Eclipse Temurin JDK 21.0.6, Gradle 9.7.1, Node.js 24.21.0, and Docker Engine 29.8.2 with Compose v5.5.1. MongoDB used the image pinned by the stack and by the test environment: `mongo@sha256:f071cbf97a6e52fb7f07ce9ca5d862ad79876bf0eba9ba97758337d740449638`.

Build the images and run the procedure:

```sh

curl -fsS http://127.0.0.1:8080/api/board
./scripts/stop-local.sh
```

## Limits of this evidence

- The procedure exercises the delivery stack on the machine of the authors, with images built from the local source checkout. It does not show the path of a recipient who has only a release bundle, which [Installation from the published bundle](#installation-from-the-published-bundle) records.
- The result covers the HTTP interface through the reverse proxy. It does not cover the browser journeys and the automated end-to-end suite against the running stack, which the end-to-end suite of this gate exercises.
- The result covers the named volume across a stop and a start. Backup and restore of the data is a separate procedure of this gate, documented in [Operations](../operations.md) and recorded in [Backup and restore roundtrip](#backup-and-restore-roundtrip).
- These results are local observations. They do not establish the status of the remote pipeline, of a review, or of a merge.

## Backup and restore roundtrip

The procedures in [Operations](../operations.md) were exercised end to end by `scripts/backup-restore-verify.sh`, exposed as the `backupRestoreVerify` Gradle task. The run used two isolated Compose projects (`sticky-notes-backup-verify-a-<timestamp>` and `sticky-notes-backup-verify-b-<timestamp>`) on the loopback ports `18090` and `18091`, so the local board volume and the local stack were never involved. The recorded results were observed on this branch once the restore namespace guard and the extended checks described below were part of the procedure.

| Check                                                                                 | Result                                                                                                                                                                                                                                                                               |
|---------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Board written on stack A                                                              | `POST /api/board/notes`, `POST /api/board/notes/{id}/checklist` and `PUT /api/board/notes/{id}/block` returned revisions 1, 2 and 3; the snapshot carried the note ID, its content, the checklist label and the blocker reason                                                       |
| `scripts/backup.sh --output … --project <stack A>`                                    | `mongodump` inside a temporary container on the pinned MongoDB image reported "done dumping `stickynotes.boards` (1 document)" and wrote `dump.archive` plus `manifest.txt` under `outputs/`, outside Git                                                                            |

| `GET /api/board` on stack A after the dump                                            | Identical to the snapshot taken before the dump, so the backup did not modify the source board                                                                                                                                                                                       |
| `scripts/restore.sh <backup> --project <stack B> --volume <volume> --force`           | After an authenticated readiness ping without a fixed sleep, `mongorestore` read the archive from stdin: "1 document(s) restored successfully. 0 document(s) failed to restore"; the manifest database matched `MONGO_DATABASE`, which the script checks before starting a container |
| `docker compose -p <stack B> up --wait`                                               | `mongo`, `api` and `web` reached `healthy` against the restored volume, so the rehydrated document passed the domain revalidation                                                                                                                                                    |

| Same restore repeated on that existing volume without `--force` and with closed stdin | Exited non-zero with "Restore cancelled.", printed no "restored successfully" line, and left the volume in place                                                                                                                                                                     |
| Teardown and residue check                                                            | The procedure tears both projects down itself, then queries `docker ps`, `docker volume ls`, and `docker network ls`: afterwards no container, volume, or network matched the run's project names or the two `<project>_restore-net` networks, so a leak fails the run               |

Run the procedure once the images exist:

```sh
./gradlew buildImages
./gradlew backupRestoreVerify
```

The observed result was `Backup/restore verification passed: snapshots equal, manifest recorded, default target created, existing volume protected, teardown clean.` The procedure was executed six times during this work: five times directly through `scripts/backup-restore-verify.sh` and once through `./gradlew backupRestoreVerify`, on macOS 15.8.1 on x86_64, with Docker Engine 29.8.2 and Compose v5.5.1, and with the MongoDB image pinned by the stack. The last run was the first one covering the extended checks — the manifest fields, the default restore target, the cancellation on an existing volume, and the residue query — and it printed no MongoDB deprecation notice.

### Limits of this result

- The procedure exercises the HTTP interface through the reverse proxy, the MongoDB persistence layer, the MongoDB tooling of the pinned image inside containers, and the stack start against a restored volume. It does not exercise the browser journeys or the images that a machine builds from a release bundle.
- The roundtrip covers `schemaVersion=1` and the single `boards` collection. It does not test a schema migration, a rollback to an image of another schema version, or the recovery of a volume that the authors were already using.
- The cancellation path was exercised with a closed stdin, so a restore into an existing volume is proven to stop without confirmation and without writing. A human answering the prompt at a terminal, and the overwrite itself through `--force` into a volume that already held data, were not exercised.
- The residue query looks for the project names of this run, so unrelated leftovers from other procedures are not reported by it.
- In these runs the container images were reused from an earlier `./gradlew buildImages` (their OCI revision label points to a pre-rebase revision of this branch) instead of being rebuilt; the change under verification touches only the shell scripts and documentation, so no image content entered the result.
- These results are local observations. They do not establish the status of the remote pipeline, of a review, or of a merge.

## Release records and integrity of a published bundle

Release `v0.24.3` publishes `sticky-notes-deliverables.zip`. The release job published it on 2026-11-04 from commit `6a6533645832d58e89dc0d395ed199c2e6626927`. The checks in this section ran against the published asset on 2026-11-04. They used no JDK, no Gradle, and no Node.js: the tools were `curl`, `unzip`, `shasum`, and a POSIX shell.

| Check | Result |
|-------|--------|
| Download of the release asset | The file measured 30,810,531 bytes. `shasum -a 256` produced `53778730b0f42d78bfa53a1177ecf52151efe6c55591d0af2bac93fbf0fb4c95`, which equals the digest that GitHub records for the asset. |
| Identity of the tag | `git rev-parse v0.24.3` prints `6a6533645832d58e89dc0d395ed199c2e6626927`. `manifest.json` records the same value in `revision`, with `version` and `imageVersion` both `0.24.3`. |
| `./scripts/verify-release.sh sticky-notes-deliverables.zip` | Printed `Release bundle verified successfully` and exited `0`. The script tests the declared deliverables and the three identity fields in `manifest.json`. It tests the stamped `VERSION` and `REVISION` build arguments in `compose.yaml` and the two versioned image names. It tests every path listed in `manifest.json` and the checksum of every file. |
| `shasum -a 256 -c SHA256SUMS` in the extracted bundle | 283 entries, all `OK`. `.env` is the only delivered runtime file that the checksum file does not cover, and `manifest.json` states the reason. |

Run the same checks:

```sh
shasum -a 256 sticky-notes-deliverables.zip      # compare with the asset digest on the release page
./scripts/verify-release.sh sticky-notes-deliverables.zip
unzip -q sticky-notes-deliverables.zip -d sticky-notes-clean
cd sticky-notes-clean && shasum -a 256 -c SHA256SUMS
```

The `releaseVerify` Gradle task runs the same script on the bundle that the current revision packages. `fullVerify` includes that task, so CI repeats the script on `main` and on every pull request. See [CI/CD](../ci-cd.md#workflow-execution-policy).

### Limits of this result

- GitHub computes the digest of the uploaded asset. The comparison proves that the downloaded bytes match the bytes that GitHub recorded at publication. It does not attest who uploaded them.
- The records describe release `v0.24.3`. The head of `main` now pins newer base images than that release does: `mongo@sha256:e0ce8c35124d4a9f9785532d1f268f39e9728ffa1cb38f46fa482436424c4bd3`, `eclipse-temurin:21-jre@sha256:0b99b3376fbb50dbf9c0af8535fdd5b8eb0d3fdfc8b1e4967f383b6919f6901a`, and `nginxinc/nginx-unprivileged:1.31.7-alpine3.24-slim@sha256:a8cb0f33d51fa107c96fd2bd3a71aaf564ec131e9d2bdf8700944f0ed8b170d7`. A recipient reads those pins only through a later release.
- No bundle rebuilt from the head of `main` was verified in this run. `./gradlew releaseVerify` verifies that bundle, and its result is the one CI records.
- The check reads files and records. It does not test the release job itself, the asset upload, or the permission that the job uses.

## Tamper rejection and data-safe restart of a published bundle

The second mode of `scripts/verify-release.sh` combines the record checks, two negative checks, and a restart that must keep the board. The run fed it the published asset of `v0.24.3`, placed at the repository path that the script expects, which `.gitignore` excludes. The run used the Compose project `sticky-notes-rollback-1793809536`, the loopback port `18095`, and the database and credentials `stickynotes_rb`.

| Check | Result |
|-------|--------|
| Bundle validation before the stack started | The extracted bundle passed the deliverable, identity, stamped configuration, path, and checksum checks. |
| Incomplete bundle | A copy without `backend/build/libs/backend.jar` was rejected with exit code `1`. |
| Tampered records | A copy whose `manifest.json` declared `99.0.0-candidate` while `SHA256SUMS` still described the original file set was rejected with exit code `1`. |
| Stack start | `mongo`, `api`, and `web` reached `healthy`, and the interface answered on `127.0.0.1:18095`. |
| Board write, stop, and restart | The run created a note through `POST /api/board/notes`, read the snapshot, ran `docker compose down` without `--volumes`, confirmed that `<project>_mongo-data` still existed, started the stack again, and compared the snapshots. They were equal, and the created note was present. |
| Final line | `Release verification passed: bundle complete, tampering rejected, data-safe rollback preserved board state.` The exit code was `0`. |
| Teardown | The procedure removed its own containers, its volume, and its network. |

Run the procedure through Gradle, which builds the images and packages the bundle of the current revision first:

```sh
./gradlew releaseVerify
```

### Limits of this result

- The restart test starts the same bundle twice. It proves that a stop without `--volumes` preserves the board across a redeploy of the same schema. It also proves that the script rejects the two tampered copies. The test never starts an image of another release, so it says nothing about compatibility between the images of two releases.
- The candidate copy that the test uses for the tamper check carries a changed `manifest.json` only. It is not a real second build, so the check proves detection of an inconsistent bundle, not behaviour across versions.
- The procedure covers `schemaVersion=1` and the single `boards` collection, like the backup and restore section above.
- These results are local observations. They do not establish the status of the remote pipeline, of a review, or of a merge.
