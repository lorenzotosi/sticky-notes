# R4 acceptance evidence

The R4 gate covers the reproducible delivery: the container images, the Compose stack, the automated checks against the running stack, the browser journeys, the published images, the backup and restore of the data, and the installation on a clean machine. The accepted behaviour is described in [requirements](../requirements.md), [architecture](../architecture.md), and [deployment](../deployment.md). The repeatable procedures are described in the [testing guide](../testing.md); this document records the results that were executed.

## Delivery stack

The stack described by `compose.yaml` was built and started on the machine of the authors. The images were produced by the build, so the stack ran the artifacts of the verified build and not a hand-made image. The results were observed on the source revision `b8480d8`.

| Check | Result |
| --- | --- |
| `./gradlew :backend:dockerImage` | Built the image `sticky-notes-backend:0.0.0-dev-eee3c04040d1` with the stable alias `sticky-notes-backend:local`; the labels carry the version and the commit |
| `./gradlew :frontend:buildWebImage` | Built the image `sticky-notes-web:local` from the Vite bundle and the Nginx configuration |
| `docker compose -f compose.yaml config` | Valid configuration, one published port, the one of the web service |
| `./scripts/start-local.sh` | `web`, `api`, and `mongo` reported `healthy` after `up --wait` |
| Published ports | `web` on `127.0.0.1:8080`; `api` and `mongo` showed their internal port without a host port |
| `GET http://127.0.0.1:8080/api/board` | Returned the board snapshot through the reverse proxy |
| `GET http://127.0.0.1:8080/api/unknown` | Returned a JSON error, not the frontend document |
| `POST http://127.0.0.1:8080/api/board/notes` | Created a note and returned the stored snapshot at the next revision |
| `./scripts/stop-local.sh` followed by `./scripts/start-local.sh` | The note, its order, and the revision were still there; the named volume `sticky-notes_mongo-data` was listed after the stop |
| `./scripts/start-local.sh --dev` | Published the API on `127.0.0.1:8080` and MongoDB on `127.0.0.1:27017`, with no published port for the web container |
| `./gradlew containerSmoke` | Automated lifecycle check in `sticky-notes-smoke`: verified non-root UIDs, host port isolation, SPA routing, CRUD persistence across stop/start, and clean volume teardown |
## Reproduction environment and commands

The results were observed on macOS 15.8.1 on x86_64, with Eclipse Temurin JDK 21.0.6, Gradle 9.7.1, Node.js 24.21.0, and Docker Engine 29.8.2 with Compose v5.5.1. MongoDB used the image pinned by the stack and by the test environment: `mongo@sha256:f071cbf97a6e52fb7f07ce9ca5d862ad79876bf0eba9ba97758337d740449638`.

Build the images and run the procedure:

```sh
./gradlew buildImages
./scripts/start-local.sh
docker compose ps
curl -fsS http://127.0.0.1:8080/api/board
./scripts/stop-local.sh
./scripts/start-local.sh
curl -fsS http://127.0.0.1:8080/api/board
```

The procedure is described in the [testing guide](../testing.md#compose-delivery-stack-r4).

## Limits of this evidence

- The procedure exercises the delivery stack on the machine of the authors, with images built from the local source checkout. It does not prove that published images start on a machine without a source checkout, a JDK, or Node.js.
- The result covers the HTTP interface through the reverse proxy. It does not cover the browser journeys and the automated end-to-end suite against the running stack, which the end-to-end suite of this gate exercises.
- The result covers the named volume across a stop and a start. Backup and restore of the data is a separate procedure of this gate, documented in [Operations](../operations.md) and recorded in [Backup and restore roundtrip](#backup-and-restore-roundtrip).
- These results are local observations. They do not establish the status of the remote pipeline, of a review, or of a merge.

## Backup and restore roundtrip

The procedures in [Operations](../operations.md) were exercised end to end by `scripts/backup-restore-verify.sh`, exposed as the `backupRestoreVerify` Gradle task. The run used two isolated Compose projects (`sticky-notes-backup-verify-a-<timestamp>` and `sticky-notes-backup-verify-b-<timestamp>`) on the loopback ports `18090` and `18091`, so the local board volume and the local stack were never involved. The recorded results were observed on this branch once the restore namespace guard and the extended checks described below were part of the procedure.

| Check | Result |
| --- | --- |
| Board written on stack A | `POST /api/board/notes`, `POST /api/board/notes/{id}/checklist` and `PUT /api/board/notes/{id}/block` returned revisions 1, 2 and 3; the snapshot carried the note ID, its content, the checklist label and the blocker reason |
| `scripts/backup.sh --output … --project <stack A>` | `mongodump` inside a temporary container on the pinned MongoDB image reported "done dumping `stickynotes.boards` (1 document)" and wrote `dump.archive` plus `manifest.txt` under `outputs/`, outside Git |
| Manifest fields | `manifest.txt` recorded `schemaVersion: 1`, `database: stickynotes`, the image reference resolved from `compose.yaml`, and a non-empty digest; the procedure requires each of them and fails when one is missing |
| `GET /api/board` on stack A after the dump | Identical to the snapshot taken before the dump, so the backup did not modify the source board |
| `scripts/restore.sh <backup> --project <stack B> --volume <volume> --force` | After an authenticated readiness ping without a fixed sleep, `mongorestore` read the archive from stdin: "1 document(s) restored successfully. 0 document(s) failed to restore"; the manifest database matched `MONGO_DATABASE`, which the script checks before starting a container |
| `docker compose -p <stack B> up --wait` | `mongo`, `api` and `web` reached `healthy` against the restored volume, so the rehydrated document passed the domain revalidation |
| `GET /api/board` on stack B | Equal to the snapshot of stack A: same note ID, content, checklist label, blocker reason, revision 3 and note order |
| `scripts/restore.sh <backup>` with no target flags | Created the documented default test target (`sticky-notes-restore-test-<timestamp>` and its `<project>_mongo-data` volume) and reported "Restore complete"; the volume was then present when queried |
| Same restore repeated on that existing volume without `--force` and with closed stdin | Exited non-zero with "Restore cancelled.", printed no "restored successfully" line, and left the volume in place |
| Teardown and residue check | The procedure tears both projects down itself, then queries `docker ps`, `docker volume ls`, and `docker network ls`: afterwards no container, volume, or network matched the run's project names or the two `<project>_restore-net` networks, so a leak fails the run |

Run the procedure once the images exist:

```sh
./gradlew buildImages
./gradlew backupRestoreVerify
```

The observed result was `Backup/restore verification passed: snapshots equal, manifest recorded, default target created, existing volume protected, teardown clean.` The procedure was executed six times during this work: five times directly through `scripts/backup-restore-verify.sh` and once through `./gradlew backupRestoreVerify`, on macOS 15.8.1 on x86_64, with Docker Engine 29.8.2 and Compose v5.5.1, and with the MongoDB image pinned by the stack. The last run was the first one covering the extended checks — the manifest fields, the default restore target, the cancellation on an existing volume, and the residue query — and it printed no MongoDB deprecation notice.

### Limits of this result

- The procedure exercises the HTTP interface through the reverse proxy, the MongoDB persistence layer, the MongoDB tooling of the pinned image inside containers, and the stack start against a restored volume. It does not exercise the browser journeys or the published images.
- The roundtrip covers `schemaVersion=1` and the single `boards` collection. It does not test a schema migration, a rollback to an image of another schema version, or the recovery of a volume that the authors were already using.
- The cancellation path was exercised with a closed stdin, so a restore into an existing volume is proven to stop without confirmation and without writing. A human answering the prompt at a terminal, and the overwrite itself through `--force` into a volume that already held data, were not exercised.
- The residue query looks for the project names of this run, so unrelated leftovers from other procedures are not reported by it.
- In these runs the container images were reused from an earlier `./gradlew buildImages` (their OCI revision label points to a pre-rebase revision of this branch) instead of being rebuilt; the change under verification touches only the shell scripts and documentation, so no image content entered the result.
- These results are local observations. They do not establish the status of the remote pipeline, of a review, or of a merge.

## Documentation publication

The documentation site was checked against the GitHub Pages deployment of `main` and against the bundle produced locally by `./gradlew documentation` on revision `e7cfb0b`. The publication procedure is described in [CI/CD](../ci-cd.md#github-pages-publication). The scenario verifies that the index opens every guide and the generated API reference, and that the documentation artifact carries the generated reference rather than a plain copy of the Markdown files.

| Check | Result |
| --- | --- |
| `./gradlew documentation verifyLicense --no-daemon` | `BUILD SUCCESSFUL`: `:commons:dokkaGeneratePublicationHtml` generated the reference and `documentation` synced the bundle |
| Bundle contents under `build/docs/` | 256 files: 22 Markdown documents (`index.md`, the guides, the specifications, the three ADRs, and the four gate-evidence documents), `openapi.yaml`, and `api/` with 177 generated HTML pages |
| Links from the published index | All 23 content links returned HTTP `200`: the guides, the specifications, the ADRs, the gate evidence, the OpenAPI document, and `api/index.html`. The only `404` observed on the site was `/favicon.ico`, a theme asset that no documentation page links to |
| Generated API reference on Pages | `api/index.html`, `api/navigation.html`, `api/styles/style.css`, `api/scripts/main.js`, `api/images/logo-icon.svg`, and the package index pages (`stickynotes.domain`, `stickynotes.contract`, `stickynotes.interop`) returned HTTP `200`; the Dokka links stayed relative and unmodified through the Jekyll build |
| Commands named in the guides | Every `./gradlew` command cited in `docs/` and `README.md` resolved to a declared Gradle task or to a script in `scripts/`; every in-document heading target in `docs/`, `README.md`, and `CONTRIBUTING.md` resolves, and the links to `api/index.html` resolve inside the generated bundle, which is not a tracked path |

The checks were executed on macOS 15.8.1 on x86_64 with Eclipse Temurin JDK 21 and Gradle 9.7.1, against the Pages deployment of `main` at revision `e7cfb0b`.

### Limits of this result

- The check reads published HTTP responses and the generated bundle. It does not drive a browser through the Dokka navigation or search widgets, so the interactive behavior of the generated reference is not exercised here.
- The result covers the documentation channel only. It proves nothing about the running application or about published images.
- The addition of `build/docs/` to the `deliverables` artifact was not exercised locally; it is observed when a full quality build runs and the release workflow packages that artifact.
- The published site reflects the `main` revision GitHub Actions published; the local bundle check covers the revision of this checkout.
