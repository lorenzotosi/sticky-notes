# Kanban Domain Requirements

This document formalizes the functional requirements and business rules for the Sticky Notes Kanban application, translating project contracts (S01, S03–S05) into testable criteria.

## 1. System Scope & Boundaries
- **Deployment & Access**: Single shared board instance hosted locally via Docker Compose; trusted single-team environment without authentication or multiple boards.
- **Out of Scope (Explicitly Deferred)**: User accounts/sessions, multi-tenancy, real-time WebSocket sync, deadlines/reminders, attachments, drag-and-drop, Kubernetes orchestration, and event sourcing.

---

## 2. Functional Requirements

### REQ-01: Note Creation and Defaults
- A new note is initialized in the `TODO` column, with default color `YELLOW`, unblocked, with an empty checklist, and appended to the end of the `TODO` column.
- The note identifier (`NoteId`) is generated by the application backend as a unique UUID.

### REQ-02: Content Length and Normalization
- Note content must contain between 1 and 500 UTF-16 code units after trimming leading and trailing whitespace and normalizing `CRLF`/`CR` line breaks to `LF`.
- An empty or blank note content is rejected (`INVALID_CONTENT`).
- Non-BMP emojis count as 2 UTF-16 code units; length validation is strictly deterministic across JVM and browser runtimes.

### REQ-03: Board and Note Capacity Limits
- A Board accommodates a maximum of 200 notes across all columns. Creating an additional note when full is rejected (`BOARD_FULL`).
- A single note accommodates a maximum of 20 checklist items. Adding items beyond this limit is rejected (`CHECKLIST_FULL`).

### REQ-04: Note Editing and Color Assignment
- The content and color of any note can be updated without mutating its identity (`NoteId`) or position.
- Allowed colors are strictly enumerated: `YELLOW`, `BLUE`, `GREEN`, `PINK`. Other color values are rejected (`INVALID_COLOR`).
- A note in `DONE` status may still have its text and color updated.

### REQ-05: Allowed State Transitions
- Notes move exclusively between adjacent lifecycle stages:
    - `TODO` $\rightarrow$ `DOING`
    - `DOING` $\rightarrow$ `TODO`
    - `DOING` $\rightarrow$ `DONE`
    - `DONE` $\rightarrow$ `DOING`
- Direct transitions `TODO` $\rightarrow$ `DONE` and `DONE` $\rightarrow$ `TODO` are prohibited and rejected (`INVALID_TRANSITION`).

### REQ-06: Work In Progress Enforcement
- Entering the `DOING` column (from `TODO` or via reopening from `DONE`) requires that the number of current `DOING` notes is strictly less than the board's `wipLimit`.
- If `DOING` count $\ge$ `wipLimit`, transition into `DOING` is rejected (`WIP_LIMIT_REACHED`).
- Blocked notes in `DOING` continue to occupy WIP capacity.

### REQ-07: In-Column Reordering
- Notes can be reordered within the same column without consuming or altering WIP capacity.
- Movement commands specify `destinationIndex` relative to the target column after removing the moving note (range: `0..targetColumnSize`). Out-of-bounds indices are rejected (`INVALID_INDEX`) without automatic clamping.

### REQ-08: Configurable WIP Limit
- The board's `wipLimit` is an integer between 1 and 20 (default: 3).
- Reducing `wipLimit` below the current number of notes in `DOING` is rejected (`WIP_BELOW_OCCUPANCY`).

### REQ-09: Note Blocking and Reasons
- Notes in `TODO` or `DOING` can be blocked by providing a mandatory reason (1..200 UTF-16 code units normalized).
- A blocked note cannot change state (`NOTE_BLOCKED`).
- A blocked note can be unblocked, have its block reason updated, or be reordered within its column.
- Notes in `DONE` cannot be blocked.

### REQ-10: Completion Checklist Integrity
- Each checklist item contains a mandatory label (1..120 UTF-16 code units) and a boolean `completed` state.
- Checklist item identifiers (`ChecklistItemId`) are generated by the backend.

### REQ-11: Guarded Transition to DONE
- A note can move from `DOING` to `DONE` only if it is not blocked AND all of its checklist items are marked `completed`.
- If any checklist item is incomplete, transition to `DONE` is rejected (`CHECKLIST_INCOMPLETE`).
- An empty checklist is considered complete by definition.

### REQ-12: Immutability of DONE Checklists & Reopening
- Once a note enters `DONE`, its checklist becomes strictly read-only: adding, updating, removing, or toggling items is rejected (`NOTE_DONE_READ_ONLY`).
- To modify checklist items of a completed note, it must first be transitioned back to `DOING`, subject to available WIP capacity.
